# 08 · 实施路线图与测试策略

> 本文档将需求（`01`）、架构（`02`）、数据（`03`）、智能体编排（`04`）、API 协议（`05`）落为**可执行的推进计划**：里程碑拆分、旧系统迁移、测试金字塔、风险登记册与工程规范。
>
> 阅读对象：单人全栈开发者（兼多智能体工程实践者）。约定：**每个里程碑结束时系统端到端可用**，旧 `knowledge/` 在功能对等验证后逐步拆除，绝不"大爆炸"切换。

## 1. 总体推进原则

### 1.1 小步快跑 + 垂直切片

- 每个 Phase 是一个**垂直切片**：从 API → 服务层 → Agent 图 → 存储 → 前端/CLI 全链路打通，而非先做完全部后端再做前端。
- 切片定义（Definition of Done，每切片必须满足）：
  1. 新增/修改代码全部通过 lint + 单测 + 集成测试；
  2. 该切片对应的 FR 有至少一条**自动化验收用例**（API 级或 E2E 级）；
  3. 关联文档（docs/ 或 README）已更新；
  4. 在本地 Compose 环境手工冒烟通过，并在 Changelog 记录。
- 单次迭代周期 ≤ 1 周；单 Phase 内任务粒度 ≤ 2 天，超过则拆分。

### 1.2 旧系统冻结迁移（功能对等测试驱动）

- `knowledge/`（import_process / query_process 两个 StateGraph、内存 task_utils、SSE 内存队列）自 Phase 1 起**冻结**：不再加新功能，仅允许修阻塞缺陷。
- 迁移路径：**新 KnowledgeAgent 工具逐个替换旧管线节点**，每替换一个节点即跑"功能对等测试"（见 4.4 迁移对等套件）：

```
旧 query_process 节点链         新 server/ 对等实现（按序替换）
─────────────────────────      ─────────────────────────────
意图路由/入口        ──────▶   Supervisor + KnowledgeAgent 路由
文档解析(文本抽取)    ──────▶   kb_import 工具 parse 子步骤
切分/清洗            ──────▶   chunking 服务（切分器可插拔）
向量化+入 Milvus     ──────▶   embedding 服务 + kb_chunks_v3
混合检索+RRF         ──────▶   kb_retrieve 工具（dense+sparse+全文）
Rerank+组装上下文    ──────▶   rerank 服务 + prompt 组装
答案生成+引用        ──────▶   KnowledgeAgent ReAct 图（引用来源 FR-08）
```

- **对等替换规则**：对同一输入（同一 PDF、同一查询），新实现与旧实现的输出在"检索命中集、答案要点、引用来源"三个维度上做对比；命中集相似度（如 Recall@k ≥ 0.9）通过后，才允许该节点下线。
- **拆除条件**：`knowledge/` 中所有节点被对等实现替换且对等套件连续 3 次全绿 → 删除旧目录（保留 git 历史），并在 `docs/README.md` 更新状态。
- **端口收敛（部署模型）**：新旧切换期**只启动 `server` 单端口**（前端/CLI 一律连它）；旧 `knowledge/` 服务不启动，仅作为代码库存在——`kb_import`/`kb_retrieve` 先以适配器方式在 `server` 进程内调用旧管线代码（补 `user_id`/`space_id` 过滤与任务化/事件化包装），对等测试通过一个替换一个；旧 `knowledge/.env` 配置迁移至 `server/.env`（02 §11.1）。
- **切换时点**：Phase 0 开发期旧系统继续运行（唯一可用）；**Phase 1 上线即切换**——用户只走新 `server` 单端口，旧服务停止，旧代码转为进程内适配器调用；节点级替换从 Phase 1 开始逐周进行（非集中重构），Phase 5 为"全部替换完 + 删除旧目录"的终点。
- 冻结期旧目录仍可被 `kb_import` 以**只读适配器**方式调用（见 3.1 双写期），双写期结束后移除适配器。

### 1.3 持续评测回归

- `eval/` 目录与代码同仓库、同 PR 演进；**任何修改检索链路、提示词、Agent 编排的 PR 必须跑对应评测**。
- CI 设置评测门槛（见 4.5）：检索命中率、RAGAS faithfulness、意图准确率**只许升不许降**（允许 ±0.5% 抖动容差）。
- 每个 Phase 结束时跑一次全量评测，结果写入 `docs/` 或 `eval/reports/` 作为历史基线。

### 1.4 切片样例：FR-05"上传 20MB PDF"如何拆成 3 个垂直切片

以 Phase 1 最重的需求为例，演示"垂直切片"的具体拆法（每个切片均可独立验收）：

| 切片 | 内容（端到端） | 验收（自动化） |
| :--- | :--- | :--- |
| S1-1 上传与任务化 | Web 上传 → MinIO 存原件 → 创建 `tasks` 记录（pending）→ SSE 推状态 | API 测试：POST 后任务存在且状态 pending；上传 20MB 文件不超时 |
| S1-2 解析入库链路 | Celery worker 执行 parse→chunk→embed→import，状态步骤树逐级推进，失败可重试 | 集成测试：eager 模式全链路；chaos：杀 worker 后恢复重试 |
| S1-3 检索闭环 | 完成后 3s 内 `kb_retrieve` 命中该 PDF 内容，前端任务面板可查看文档并提问 | E2E：上传→完成→提问命中；对等套件：与旧 query_process 对比 |

> 拆分原则：**每个切片都从"用户可感知的端"（API/前端）打通到"数据落库"**，不做纯后端中间层切片；切片的测试在完成当天即入 CI。

### 1.5 单人开发节奏约定

- 分支策略：`main`（可部署） + `feat/<phase>-<slice>`（功能分支） + `fix/*`；每个 Phase 结束打 tag `v0.<phase>.0`。
- 每个 Phase 开始先写"本 Phase 测试计划"（在本文档对应小节勾选），结束写"验收记录"（附录 A）。
- 本地一天两提交节奏：上午完成一个切片 + 测试，下午跑评测/手工冒烟 + 复盘。
- 周节奏：周一规划本周切片清单 → 周二至周四实现 → 周五评测 + 补测试 + 更新文档/Changelog；每周结束 `main` 必须可部署。

### 1.6 路线 A（求稳）执行细则（ADR-018）

决策：**求稳优先**。增强类功能一律"先验证、后投入"，以门禁代替计划排期：

| 增强类功能 | MVP 范围 | 投入完整版的门禁 | 风险 |
| :--- | :--- | :--- | :--- |
| 记忆 | 仅 L0 原文检索 + L1 显式条目（用户"记住"+Agent 半自动提议），禁止自动抽取 | 注入增益消融评测通过（07 §4.2）+ LoCoMo 基准达标 | R13/R14 |
| 图谱 | 轻量"实体→文档映射表"（P2 验证） | 图谱检索增益超过阈值（对比无图谱基线） | R15 |
| 外部 Agent | 评估性冒烟（最小适配器 + 单次委托） | 持续委托的真实诉求（≥2 次/周） | R12 |
| 自动整理（夜间） | 不启用（仅 TTL 过期与纯重复去重） | 记忆增强门禁通过后，按 03 §10.1 增量执行 | R14 |
| 多用户/admin | 基础版 P1（隔离是安全底线） | 成本看板/完整审计随用量增长逐步完善 | — |

**目标**：记忆四类完整生命周期 + 评测体系落地 + 成本与性能达标。

## 3. 迁移与数据升级

### 3.1 旧 Milvus 集合 → kb_chunks_v3

旧集合：`kb_chunks_v2`（知识切片）、`item_names`（商品名）、`entity_names`（实体名）。目标：合并为统一 `kb_chunks_v3`（含 `domain`、`space_id`、`user_id`、`source` 字段，对齐 `03`）。

| 步骤 | 动作 | 说明 |
| :--- | :--- | :--- |
| 1. 准备 | 迁移脚本 `server/scripts/migrate_milvus_v2_to_v3.py`（幂等、可断点续跑、写迁移日志集合 `migration_logs`） | 先在 staging 库跑通并留快照 |
| 2. 双写期 | 新写入同时写 v2（只读适配器路径）与 v3；`kb_retrieve` 只读 v3 | 双写期 ≥ 1 周，期间新文档只入 v3 |
| 3. 校验 | 抽样对比：每集合抽 ≥ 1000 条，比对 count、`text` 字段一致率、向量维度；抽样 query 对比 v2/v3 检索 Recall@k ≥ 0.9 | 校验失败则回滚（见 3.4） |
| 4. 切换 | `kb_import` 只写 v3；删除 v2 只读适配器；旧集合置 `readonly` 保留 2 周 | 切换后立即跑对等套件 + 越权矩阵 |
| 5. 下线 | 2 周观察期无异常后 drop `kb_chunks_v2`/`item_names`/`entity_names`（保留导出备份） | 在 Changelog 记录下线时间 |

### 3.2 旧 Mongo 库 `knowledge` → `shopkeer`

- 旧库仅保留会话历史等少量可迁移数据；**任务状态不迁移**（见 3.3）。
- 迁移步骤：① 旧会话/文档元数据导出为 JSON 快照 → ② 按新 schema（`user_id`/`space_id` 必填，归属"迁移管理员"个人空间）导入 `shopkeer.sessions`/`documents` → ③ 校验 count 与抽样字段 → ④ 旧库 `knowledge` 改名 `knowledge_archive_<date>` 保留，2 周后删除。
- 密码/密钥类数据**一律不迁移**（旧系统无用户体系，用户全部重新注册，FR-01 新认证）。

### 3.3 旧任务内存态：丢弃不迁移

- 旧 `task_utils` 内存字典 + SSE 内存队列中的进行中任务**直接丢弃**：状态无法可靠重建，且迁移价值为零。
- 新任务系统（Mongo `tasks` 集合持久化状态 + Celery）从零开始；迁移脚本只做"旧任务全部标记为 `cancelled(legacy)`"的审计记录，保证运营侧无孤儿任务困惑。

### 3.4 回滚方案

| 阶段 | 回滚触发 | 回滚动作 | 代价 |
| :--- | :--- | :--- | :--- |
| 双写期 | 校验失败（Recall < 0.9） | 停 v3 写入，`kb_retrieve` 回切 v2 只读 | 低：v2 未删 |
| 切换后 2 周内 | 检索线上异常率上升 | `kb_import`/`kb_retrieve` 回切 v2 适配器（代码开关 `FEATURE_USE_V3=false`） | 中：双写期数据需重放 |
| 旧集合下线后 | 极端情况需恢复 | 从备份集合/导出 JSON 重建 v3 子集 | 高：仅灾难场景 |
| 代码回滚 | 任一 Phase 验收失败 | 分支回退 + tag 回滚（`main` 保持可部署） | 低：CI 门槛拦截 |

## 4. 测试策略（金字塔）

### 4.1 总览与目录结构

```
tests/
├── unit/            # 节点/服务/工具单测（LLM mock）
├── integration/     # 图级（录制-回放）、API 级、Celery
├── e2e/             # Playwright 前端 + CLI 冒烟
├── parity/          # 新旧功能对等套件（迁移专用）
├── security/        # 越权矩阵 / prompt 注入 / JWT
└── chaos/           # worker 杀进程、Redis 故障
eval/                # 意图集 / 检索集 / 答案集（评测回归）
```

原则：单测快（< 2s/用例）、不碰外部依赖；集成测试默认 mock 外部 LLM/第三方 API，可开关真实调用；E2E 在 CI 的 headless 环境跑关键路径。

**测试数据管理**：固定语料入库 `tests/fixtures/`（3 个 PDF 含 1 个 20MB、5 个 md/图片、50 条跨域 query、注入样例文档）；LLM 录制快照与评测集统一版本化（`fixtures/versions.json`），避免测试数据漂移导致"测试过、线上挂"。测试库 `shopkeer_test` 每次运行前重建，保证幂等。

### 4.2 单元测试

| 对象 | 策略 | 工具 |
| :--- | :--- | :--- |
| Agent 节点（纯逻辑） | LLM 返回 mock 结构化结果，断言状态流转/工具调用序列 | pytest + pytest-mock + 快照（syrupy） |
| 工具（kb_retrieve/kb_import/paper_search…） | 输入输出契约测试；检索打分/切分/清洗逻辑全真 | pytest |
| pymilvus 客户端 | 嵌入式/内存 mock（Milvus Lite 或 fake 客户端），断言 collection/过滤条件 | pytest + milvus-lite |
| Mongo 访问层 | mongomock 或 testcontainers-mongo，断言 `user_id`/`space_id` 过滤恒存在 | mongomock / testcontainers |
| 状态机/SSE 协议 | 纯内存跑状态迁移全路径（含非法迁移拒绝） | pytest |

### 4.3 集成测试

- **LangGraph 图级**：默认**录制-回放快照**（首次用真实 LLM 录制，之后回放）；提供 `EVAL_LLM_REAL=1` 开关跑真实 LLM 的"真实验收"模式；断言图节点执行序、HITL 中断点、Critic 重试路径。
- **API 级**：FastAPI TestClient + 每个测试独立测试库（`shopkeer_test`）；覆盖认证、空间、上传、检索、任务、SSE（用 ASGI 传输层直接读事件流）。
- **Celery 任务测试**：① `task_always_eager=True` 模式下跑全任务逻辑（快速回归）；② 一个真实 worker 冒烟 job（`pytest -m celery_real`）验证 broker/结果后端连通与重试（NFR-04）。
- **迁移对等套件（`tests/parity/`）**：固定语料（3 个 PDF + 50 条 query），对比新旧实现输出（见 1.2），CI 必跑。

**关键集成用例清单**（命名即文档，`test_<场景>_<断言>`）：

```
tests/integration/
├── test_graph_knowledge_agent.py    # test_hitl_clarify_pauses_graph / test_critic_retry_once
├── test_api_auth.py                 # test_refresh_rotation_rejects_old_token
├── test_api_upload.py               # test_upload_20mb_succeeds / test_upload_duplicate_detected
├── test_api_sse.py                  # test_task_events_streamed_in_order
├── test_celery_tasks.py             # test_import_retry_twice_then_fail / test_task_cancel_stops_worker
└── test_space_isolation.py          # test_search_scoped_by_space_id
```

### 4.4 端到端测试

- **Playwright（Web）**：登录 → 上传 PDF（fixture 文件）→ 任务面板看到步骤树 → 检索命中 → 聊天（SSE 流式）→ HITL 澄清确认 → 完成；同一套件覆盖空间切换与越权前置场景。
- **CLI 冒烟**：`cli chat "…"`、`cli upload`、`cli task status` 各一条断言，串起认证 + 任务链路。
- 运行环境：CI 内 Docker Compose 全栈起（Mongo/Milvus/Redis/MinIO + API + worker），Playwright 无头。

### 4.5 评测回归（`eval/`）

| 评测集 | 内容 | 门槛（CI 硬性） |
| :--- | :--- | :--- |
| 意图集 | 50 条跨域语料（knowledge/dev/research/life/general） | 准确率 ≥ 90%（FR-09） |
| 检索集 | query → 期望 chunk 标注（≥ 60 条，覆盖空间过滤） | Recall@k ≥ 0.85，且不下降 > 1% |
| 答案集 | 问答对 + 引用标注 | RAGAS faithfulness ≥ 0.8、answer relevancy ≥ 0.7，不下降 |
| 成本基线 | 固定 query 集的 token 消耗 | 单任务 token 超预算即失败（NFR-08） |

- 门槛实现：`eval/run.py --set intent|retrieval|answer --threshold`，输出 JSON 报告到 `eval/reports/`；CI 对比基线文件（`eval/baselines/*.json`），超差即红。
- 检索链路、提示词、Agent 编排相关 PR 必须附评测结果；LLM-as-judge 的 judge 提示词本身入评测（防 judge 漂移）。

### 4.6 安全测试

- **越权矩阵测试**：对资源类型（文档/切片/记忆/任务/空间/清单/经验）× 操作（读/写/删）× 访问者（他人用户、他人空间成员、viewer 越权写）全组合，逐一断言 403/404（对齐 NFR-05）；覆盖 REST、SSE、CLI 三条通道。
- **Prompt 注入样例集**：文档内容含"忽略以上指令"类文本，断言 agent 不执行注入动作（数据/指令隔离，NFR-07）；样例集固化在 `tests/security/`，CI 必跑。
- **JWT 测试**：过期 access 拒绝、refresh 轮换、旧 refresh 复用被拒、退出后令牌失效。

### 4.7 混沌 / 可靠性

| 场景 | 验证点 | 方式 |
| :--- | :--- | :--- |
| worker 杀进程 | 进行中任务状态恢复为 `failed(retryable)` → 自动重试 ≥ 2 次 → 成功/最终失败（NFR-04） | 脚本 kill -9 worker，断言任务终态 |
| Redis 故障 | 任务提交失败返回明确错误码；恢复后新任务正常；不产生脏数据 | 停 Redis 容器后提交任务 |
| Milvus 不可用 | 检索降级路径（返回 503 + 明确错误，不静默空结果） | 停 Milvus 容器 |
| 第三方 API 超时 | paper_search/shopping_search 超时降级（缓存命中或明确失败） | mock 超时 |

> 混沌场景在 CI 用单独 job 运行（不稳定标签 `chaos`，允许手动触发），不阻塞普通 PR。

### 4.8 CI 流水线设计（GitHub Actions，可移植自建）

```yaml
# .github/workflows/ci.yml 概要
jobs:
  lint:      ruff check + ruff format --check + mypy（可选严格模式，先开增量）
  unit:      pytest tests/unit（快，< 5min）
  integration:
    services: mongo/milvus-lite/redis/minio
    run:      pytest tests/integration -m "not celery_real"
  celery_real:  起真 worker 跑 celery_real 标记用例
  parity:    pytest tests/parity（迁移对等）
  eval:      eval/run.py intent + retrieval + answer（对比基线，PR 触发 + 每夜全量）
  security:  pytest tests/security（越权矩阵 + 注入 + JWT）
  e2e:       docker compose 全栈 + Playwright（仅 main / release 分支与手动）
  build:     构建 server 镜像 + web 产物 + cli 打包（冒烟启动 /health）
```

- 门禁顺序：lint → unit → integration → (parity/eval/security) → e2e/build；`main` 分支强制全绿 + 评测基线更新才可合入。
- 每日 03:00 定时全量评测 + e2e，失败自动开 issue。

## 6. 工程规范

### 6.1 代码规范

- **Python**：ruff（lint + format，行宽 100），类型标注必须（mypy 先增量后严格）；命名遵循 PEP8；服务层禁止裸 `requests` 调用，统一走封装客户端。
- **TypeScript/Vue3**：ESLint + Prettier；组件目录按 feature 组织；状态管理（Pinia）禁止在组件内散落全局状态。
- 禁止 `except Exception: pass`；第三方调用必须超时 + 重试策略（对齐 4.7）。

### 6.2 提交规范（Conventional Commits）

```
feat(agent):  KnowledgeAgent 接入 kb_retrieve 工具
fix(task):    状态机重试计数重置错误
test(parity): 新增 v2/v3 检索对等用例
docs(08):     更新 Phase 1 验收记录
chore(ci):    评测门槛接入 PR 检查
```
- 每个提交必须通过本地 lint + 相关单测；提交信息关联 FR/风险编号（如 `feat(kb): FR-05 步骤树`）。

### 6.3 PR 评审清单（单人开发 = 自审清单）

1. 变更是否对应用户故事/FR？测试是否补齐（单测/集成/对等/安全相关）？
2. 所有存储访问是否带 `user_id`/`space_id` 过滤（grep 复查）？
3. LLM 调用是否有预算上限与超时？外部 API 是否限流/缓存？
4. 错误码与日志是否对齐 `05` 文档规范？敏感信息（密钥/文档内容）是否进日志？
5. 是否更新 docs/ 与 Changelog？评测基线是否需更新？

### 6.4 文档规范

- 新功能/接口变更必须同步更新对应 `docs/0X-*.md`；新增环境变量必须更新 `.env.example` 与部署文档；`docs/README.md` 文档地图保持最新。

### 6.5 配置管理（.env 分层）

```
.env.example          # 模板，提交仓库
.env.local            # 本地开发（gitignore）
.env.test             # CI/测试库配置（gitignore）
.env.prod             # 部署环境（服务器上，gitignore）
```
- 所有配置经 pydantic-settings 校验加载；`settings` 单例禁止测试间污染；密钥只入环境变量/密钥管理，不入仓库。

### 6.6 版本号策略（SemVer）

- `MAJOR.MINOR.PATCH`：Phase 里程碑完成 → MINOR+1（v0.1.0…v0.5.0）；缺陷修复 → PATCH+1；阶段一发布 → v1.0.0。
- 每版本 tag + Changelog（Keep a Changelog 风格）；`main` 永远可部署。
