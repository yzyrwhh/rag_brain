# 02 · 系统架构与部署

## 1. 架构风格与分层

采用 **DDD 分层 + 事件驱动任务执行** 的混合风格：表现层与应用层走传统三层，领域层是多智能体编排核心，基础设施层提供可插拔能力。

```
┌──────────────────────────────────────────────────────────────────┐
│ 表现层 Presentation                                                │
│  Web SPA (Vue3)         CLI (Typer)          (阶段二) PWA          │
└───────────────┬──────────────────────────────────────────────────┘
                │ HTTPS / WSS / SSE
┌───────────────▼──────────────────────────────────────────────────┐
│ 网关与API层 API Gateway (FastAPI)                                 │
│  auth 中间件 → 路由 → 限流 → 参数校验(Pydantic v2) → 错误码统一     │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│ 应用层 Application                                                 │
│  ChatService / TaskService / KnowledgeService / AgentService      │
│  MemoryService / IntegrationService                                │
│  ┌───────────── 任务调度 ─────────────┐                            │
│  │ 同步通道: 图内直接执行(SSE)        │                            │
│  │ 异步通道: Celery + Redis 队列      │                            │
│  └────────────────────────────────────┘                            │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│ 领域层 Domain —— 多智能体编排 (LangGraph)                          │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │ Supervisor(主管) → 意图识别/路由                            │   │
│  │   ├─ KnowledgeAgent(知识)  ├─ DevAgent(开发)               │   │
│  │   ├─ ResearchAgent(研究)   └─ LifeAgent(生活)              │   │
│  │ Planner(规划) → Executor(执行, ReAct) → Critic(反思/重试)   │   │
│  │ MemoryManager(工作/情景/语义/程序记忆)   GuardAgent(安全)    │   │
│  └───────────────────────────────────────────────────────────┘   │
│  子图嵌套: Supervisor 图 → 域 Agent 子图 → 工具调用循环             │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│ 基础设施层 Infrastructure                                          │
│  工具注册中心(MCP) │ 数据服务层(数据中台) │ MongoDB │ Milvus │ Neo4j │
│  Redis │ MinIO │ 百炼LLM                                            │
│  LangSmith(trace) │ 日志/指标 │ 对象存储 │ Docker沙箱(阶段二)       │
└──────────────────────────────────────────────────────────────────┘
```

**分层原则：**

- 领域层不依赖 FastAPI/Celery：图节点只通过接口（`ports`）调用基础设施，便于单测与框架替换。
- 应用层负责事务边界、权限校验、任务调度，不写业务规则。
- 所有跨层数据用 Pydantic 模型传递（`schemas/` 为 DTO，`domain/` 为实体）。
- **数据服务层（数据中台，ADR-014）**：领域层与基础设施之间的统一数据访问层，Agent 与业务服务一律通过它读写存储，`user_id`/`space_id` 隔离、审计、缓存、限流在此单点强制（详见 §9）。

## 3. 任务执行模型（核心设计）

### 3.1 两类执行路径

| 类型 | 判定 | 通道 | 场景 |
| :--- | :--- | :--- | :--- |
| 同步快任务 | 预估 ≤ 30s（RAG 问答、简单对话） | 请求内执行，SSE 推送增量 | FR-03 |
| 异步长任务 | 预估 > 30s（综述、批量入库、论文检索+入库） | Celery worker 执行，状态持久化 + 事件推送 | FR-04 |

**判定策略**：Supervisor 意图识别时同时输出 `task_type: sync|async`；`sync` 执行中若超时自动升级为异步（兜底）。

### 3.2 任务状态机

```
PENDING ──▶ PLANNING ──▶ EXECUTING ──▶ REVIEWING ──▶ COMPLETED
   │            │            │  ▲          │
   │            │            ▼  │          │
   │            └────────▶ AWAITING_INPUT ◀─┘ (澄清/确认, HITL)
   │                           │
   └──────────▶ FAILED ◀───────┘  (可重试, retry_count ≤ 3)
                        │
                        └──▶ CANCELLED (用户取消/超时)
```

- **持久化**：任务状态与事件写入 Mongo（`tasks` + `task_events`），进程崩溃后可从最后已提交状态恢复（图执行用 LangGraph `interrupt` + checkpoint，阶段一至少做到"任务记录可恢复、执行可重跑"）。
- **重试**：节点级重试（LLM 超时/限流）与任务级重试（失败后重启任务，带 `resume_from`）。
- **取消**：`POST /tasks/{id}/cancel` → worker 端通过 LangGraph 中断/信号终止，状态置 CANCELLED。
- **预算**：每任务 `max_tokens_budget`（默认 50k）、`max_steps`（默认 30）、`timeout`（默认 15min），超限触发降级（截断工具调用、仅输出已得结果）。

### 3.3 事件流（驱动前端可视化的唯一来源）

任务执行中产生有序事件：`task.ready → task.plan → node.start / node.end → tool.call / tool.result → agent.thinking → clarify(需用户输入) → task.completed / task.failed / task.cancelled`。

- 同步路径：事件直接推入 SSE 队列（复用现有 `sse_tool`，升级为按 `task_id + user_id` 双键）。
- 异步路径：worker 写 `task_events`（Mongo）→ 同时 publish 到 Redis channel `task:{task_id}`；WebSocket/SSE 订阅转发（阶段一用 SSE 轮询 `events/after` 游标兜底，阶段二上 WebSocket）。
- 事件协议详见 05 文档。

## 4. 技术选型决策（ADR 明细）

| 决策点 | 选项 | 选择 | 理由 |
| :--- | :--- | :--- | :--- |
| 编排框架 | LangGraph / AutoGen / CrewAI | **LangGraph** | 图式显式可控、SubGraph 嵌套、与现有代码融合、interrupt 支持 HITL |
| 追踪 | LangSmith | **LangSmith** | 多 agent trace、token 统计、prompt 版本对比 |
| 任务队列 | Celery / arq / FastAPI BackgroundTasks | **Celery + Redis** | 成熟、重试/优先级/worker 管理完善；节点代码多为同步库（pymilvus/BGE），celery 契合 |
| Web 框架 | FastAPI | **FastAPI** | 现有资产，SSE/WS 原生支持，Pydantic v2 |
| 数据库 | MongoDB | **MongoDB 7** | 现有资产；文档模型契合消息/任务/配置类数据 |
| 向量库 | Milvus | **Milvus 2.6** | 现有资产；标量过滤 + 混合检索（sparse 需 BGE-M3） |
| 缓存/队列/SSE | Redis | **Redis 7** | 队列 broker、事件 pub/sub、限流、会话缓存 |
| 对象存储 | MinIO | **MinIO** | 现有资产；原文档、图片、论文 PDF |
| LLM | 百炼 qwen 系列 | **qwen-flash/plus/max + vl** | 现有资产；性价比高；兼容 OpenAI 协议 |
| 嵌入 | text-embedding-v4 / BGE-M3 | **text-embedding-v4（API）为主，BGE-M3 本地可选** | API 免运维；本地 BGE 用于离线/隐私场景（现有代码保留） |
| 重排 | bge-reranker-large | **bge-reranker-large（本地）** | 现有资产 |
| 前端 | Vue3 / React | **Vue3 + TS + Vite + Pinia** | 生态成熟、开发效率高、与现有静态页渐进迁移 |
| CLI | Typer / Click | **Typer** | 类型友好、与 pydantic 配合好 |
| 代码沙箱 | 本机执行 / Docker / 云端 | **Docker 沙箱（阶段二）** | 隔离与安全优先 |
| 图谱存储 | 关系集合 / Neo4j / 图数据库即服务 | **Neo4j 5.x（FR-26）** | 实体/关系/多跳查询与脑图投影原生支持，与向量检索互补 |
| 全文原件 | 仅 MinIO / 全文索引引擎 / 预签名 URL | **MinIO 预签名 + Mongo `document_texts`（FR-27）** | 原件下载与全文加载双通道，无需引入全文检索引擎 |
| 文档解析 | MinerU / MarkItDown / 现有 pdf_md | **优先复用现有 pdf_md + md_img，评估 MinerU 提升表格/公式质量** | 减少返工，质量提升单独立项 |

## 7. 安全架构

| 主题 | 设计 |
| :--- | :--- |
| 认证 | JWT：`access(15min) + refresh(7d)`，refresh 旋转 + 吊销列表（Redis）；密码 bcrypt(12) |
| 授权 | 中间件注入 `current_user`；数据访问一律带 `user_id` 过滤；空间成员校验（owner/member/viewer） |
| 数据隔离 | Milvus 检索 filter：`space_id in user_spaces AND visibility`；Mongo 查询默认带 `user_id`；MinIO 对象键带 `user_id/space_id` 前缀 |
| 密钥管理 | 第三方 API key 用 Fernet 加密存 Mongo（`integrations`），解密仅限 worker 内存；LLM 密钥走环境变量 |
| Prompt 注入 | 检索内容封装为 `<data>…</data>` 不可信区；GuardAgent 检测注入模式并降级；工具调用前校验参数类型 |
| 外链安全 | 生活域只输出链接，不携带用户会话凭证；链接统一经 `redirect` 端点（可审计、可封禁域名） |
| 审计 | `audit_logs`：登录、删除、导入、记忆变更、敏感工具调用（写者追责） |
| 限流 | 登录/注册按 IP+账号；聊天/任务按用户 QPS（Redis 令牌桶） |
| 输入校验 | Pydantic v2 全量校验；文件上传校验魔数、大小上限（100MB）、类型白名单 |

## 8. 可扩展性预留

- **新域 Agent**：实现 `BaseWorker` 接口 + 注册到 `agent_registry` + 前端 Agent 管理页可见，即可接入（04 文档）。
- **新工具**：MCP 工具注册中心自动发现（stdout/SSE 两种 MCP 传输），无需改代码。
- **多实例**：API 无状态（session 存 Mongo + Redis），worker 独立扩展；Milvus/Mongo 为共享存储。

## 9. 数据服务层（数据中台，ADR-014）

### 9.1 为什么需要

Agent 若直连 Mongo/Milvus/Neo4j/MinIO，会出现：检索漏加 `user_id` 过滤（越权）、无统一审计、缓存各自为政、跨库事务散落各处。**数据服务层把所有存储访问收口为一套带强制策略的 API**。

### 9.2 结构

```
Agent 图节点 / 应用服务
        │  只允许调用 DataService 接口（Pydantic DTO 出入）
        ▼
┌──────────────────────────────────────┐
│  DataService（数据中台）               │
│  ┌────────────────────────────────┐  │
│  │ 策略层: 隔离校验(user/space)     │  │
│  │        审计钩子 / 限流 / 缓存    │  │
│  ├────────────────────────────────┤  │
│  │ 领域服务: KbService GraphService │  │
│  │  MemoryService TaskService      │  │
│  │  UserService FulltextService    │  │
│  ├────────────────────────────────┤  │
│  │ Repository 层（薄封装，含过滤）   │  │
│  │  MongoRepo MilvusRepo Neo4jRepo │  │
│  │  MinioRepo RedisRepo LLMRepo    │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

### 9.3 强制策略

| 策略 | 实现 |
| :--- | :--- |
| 隔离 | 每个 Repository 方法签名必须携带 `user_id`（+可选 `space_ids`），Repository 内拼入查询条件；单测断言"查询恒含隔离字段" |
| 审计 | 写操作（导入/删除/记忆/工具确认/外部 Agent 调用）经审计钩子写 `audit_logs` |
| 缓存 | 读接口支持显式缓存（Redis），如检索结果、预签名 URL（TTL 内复用） |
| 限流 | 按用户/接口维度在策略层统一限流 |
| 跨库一致性 | 导入等跨库流程由对应 Service 编排，失败回滚/幂等（见 03 §7） |

### 9.4 关键接口清单

```
KbService:       retrieve(混合检索) / import / list_docs / get_fulltext / get_download_url
GraphService:    query(实体/关系) / mindmap(子图投影) / neighbors(1-2跳扩展) / upsert_batch
MemoryService:   search / write / consolidate(定期整理触发) / capture(点子) / progress(进展)
TaskService:     create / get / update_status / append_event / cancel
UserService:     get_user / check_role / quota 查询与扣减
FulltextService: assemble_fulltext(分片组装) / stream(预算内分节读取) / presign(原件下载)
```

> 详细 schema 与集合定义见 `03`，Agent 工具如何使用见 `04`，对外 API 见 `05`。

## 10. 技术栈问题映射与备选否决记录

> 每个技术栈回答三个问题：**解决什么痛点 / 为什么不选替代品 / 落位在哪**。与 01 §8 痛点矩阵互查，确保"没有为技术而技术"。

| 技术栈 | 解决的痛点 → 方案 | 为什么不选替代品 | 落位 |
| :--- | :--- | :--- | :--- |
| LangGraph | 复杂多步编排不可控、HITL 中断恢复难 → 图式状态机 + SubGraph + interrupt | AutoGen（对话式难显式控流）、CrewAI（封装重、黑盒）、自研（重复造轮子） | 04 |
| LangSmith | 多 agent 链路无法排障、token 无统计 → 全链路 trace + 成本归因 | 自研 trace 成本高于收益；print 调试不可行 | 07 §6 |
| Celery + Redis | 长任务不可靠（重启丢、无重试）→ 异步队列 + 重试 + 定时（beat） | arq（生态小）、FastAPI BackgroundTasks（进程内、不可靠）、Temporal（重、学习成本高） | 02 §3 |
| FastAPI | SSE/WS 实时交互 + Pydantic v2 校验 → 原生支持 | Flask（SSE 无成熟异步方案）、Django（重、与 async agent 栈割裂） | 05 |
| MongoDB | 消息/任务/记忆/配置天然文档化、schema 弹性 → 文档模型 | PostgreSQL+JSONB（嵌套查询弱、迁移重）、Redis 纯 KV（不适合结构化） | 03 |
| Milvus | 向量检索 + 标量过滤 + 混合检索（稀疏+稠密+RRF） | Chroma（无成熟标量过滤/多租户）、FAISS（无服务、无过滤）、Elasticsearch kNN（资源重、运维贵） | 03 §4 |
| Neo4j | 关系/多跳/脑图/引用网络 → 图查询 | 自研关系表（多跳深查性能差）、图即服务（成本高、数据出境） | 03 §8 |
| Redis | 队列/事件发布/限流/缓存/分布式锁多合一 | RabbitMQ（仅队列，缺限流/缓存）、内存态（重启丢） | 02 §3 |
| MinIO | 原文档/图片/论文对象存储 + S3 兼容 | 本地磁盘（无备份/扩展）、云 OSS（部署依赖云） | 03 §6 |
| qwen 系列（flash/plus/max/vl） | 成本×质量分级（路由用 flash、规划用 plus、复杂代码用 max） | GPT-4o（贵）、本地开源模型（质量/运维）、单一模型（成本失控） | 07 §1 |
| BGE 嵌入/重排（本地） | 离线/隐私场景嵌入与精排，调用费固定 | 纯 API 嵌入（隐私、成本）、大模型做精排（贵且慢） | 07 |
| Vue3 + TS | SPA + SSE 实时面板 + 生态成熟 | React（可用，团队栈偏好）、原生 HTML（现状痛点：无状态管理） | 06 |
| Typer CLI | CLI 复用同一 API/SSE 协议，调试快 | 手写 requests 脚本（重复、无协议复用） | 06 §9 |
| Docker 沙箱 | 代码执行隔离 → 防逃逸/资源限制 | 本机执行（危险）、云端执行（依赖网络/成本） | 04 §11 |
| JWT + bcrypt | 无状态认证、多副本扩展、密码安全 | 服务端 session（有状态、多副本同步难） | 02 §7 |
| SSE（先）→ WebSocket（后） | 任务事件流 + 游标续传，浏览器原生 | 一上来就 WS（复杂度高，个人规模无必要） | 05 §10 |
| BM25（阶段一记忆检索） | 无 embedding 也可召回，降级链 | 强制向量（过度设计、成本高） | 03 §10.3 |

**备选方案否决记录**（被评估后不采用的方案，防止未来重复调研）：

| 备选方案 | 否决原因 |
| :--- | :--- |
| PostgreSQL + pgvector | 现有 Mongo/Milvus 资产已覆盖；嵌套文档查询与任务/消息模型不契合 |
| Elasticsearch | 检索/全文需求 Milvus+BM25 已满足，ES 运维与资源成本过高 |
| Chroma / FAISS / Qdrant | 多租户标量过滤与混合检索能力不足，或需额外部署 |
| RabbitMQ / Kafka | 队列需求单一，Redis Stream/List 足够；Kafka 个人规模过重 |
| Temporal | 工作流编排 LangGraph 已覆盖；Temporal 学习与运维成本高 |
| AutoGen / CrewAI | 对话式多智能体不适合本系统的显式图控制与 HITL 需求 |
| Dify / FastGPT / Coze 低代码平台 | 可定制性不足，无法承载自研多智能体编排与记忆系统 |
| SQLite 全量存储 | 记忆检索可先用 BM25（借鉴 TencentDB-Agent-Memory），但业务数据仍需 Mongo 的多租户与弹性 |
| 本地 LLM 全量替换 | 质量与成本权衡不划算，qwen API 分级更优 |

### 11.2 同步聊天时序（快任务）

```
用户 → POST /chat/stream ─┐
  FastAPI 校验 JWT/限流 → 创建任务(PENDING) → 注册 SSE 队列 → 返回 task.ready
  → Supervisor 图 invoke（同步）→ guard → intent
  → 域 Agent 子图（检索/生成，push_event 直推 SSE 队列）
  → finish 节点写 message + 记忆 → task.completed → 关闭队列
前端：EventSource 消费事件 → 渲染消息与任务面板
```

### 11.3 异步任务时序（慢任务）

```
用户 → POST /tasks → FastAPI 建任务(PENDING) → Celery 入队 → 返回 task_id
worker: 任务置 PLANNING → Supervisor 图 invoke（checkpointer 持久化）
  → 每节点 push_event → 写 Mongo task_events + Redis 发布 task:{id}
  → clarify → 任务置 AWAITING_INPUT + checkpoint 落库 → 等待 POST /tasks/{id}/respond
  → resume(Command(resume=payload)) → 继续 → COMPLETED → 写结果与 cost
前端：GET /tasks/{id}/events?after_seq=N（SSE 游标续传）消费事件；断线重连补发
```
