# 03 · 领域模型与数据设计

> 本文定义限界上下文、核心实体及其在 MongoDB / Milvus / Redis / MinIO 中的落地 schema。命名是全局契约，04（智能体）、05（API）、06（前端）均以本文为准。

## 1. 限界上下文（Bounded Contexts）

```
┌─────────┐ ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌─────────┐ ┌────────────┐
│ Identity│ │  Chat   │ │Knowledge │ │  Agent   │ │  Task   │ │  Memory    │
│ 用户/会话│ │ 对话消息 │ │ 空间/文档 │ │ 配置/工具 │ │ 任务/事件│ │ 长期记忆    │
└─────────┘ └─────────┘ └──────────┘ └──────────┘ └─────────┘ └────────────┘
```

- **Identity**：用户、认证。无对外业务逻辑。
- **Chat**：会话与消息（消息关联 task_id 便于回溯）。
- **Knowledge**：知识空间、文档、切片、检索。切片本体在 Milvus，元数据在 Mongo。
- **Agent**：Agent 定义（系统/个人）、工具注册、提示词版本。Agent 执行产物是 Task。
- **Task**：任务状态机、事件流、成本统计。异步执行的中枢。
- **Memory**：语义记忆条目（长期事实、偏好、经验），向量在 Milvus，正文与元数据在 Mongo。

## 2. 核心实体关系

```
User 1───N Session 1───N Message
User 1───N Task 1───N TaskEvent
User 1───N KnowledgeSpace 1───N SpaceMember
KnowledgeSpace 1───N KnowledgeDocument 1───N Chunk(→Milvus)
User 1───N AgentConfig (个人) ;  SystemAgentConfig (系统, 共享只读)
User 1───N MemoryEntry (语义记忆)
User 1───N Integration (第三方配置)
User 1───N Feedback (对答案的评价)
```

## 7. 数据一致性与生命周期

- **最终一致性**：导入链路 = 上传 → Mongo 元数据(pending) → 解析/切分/嵌入 → 事务性写 Milvus → 元数据(completed) + chunk_count。失败时元数据置 failed，可重试（幂等：按 checksum 跳过已完成 chunk）。
- **幂等键**：文档 `checksum` + `space_id` 去重；任务 `client_request_id` 防重复提交。
- **TTL/清理**：`task_events` 保留 30 天归档；临时会话消息可配置保留期；用户注销 → 级联删除 Mongo/Milvus/MinIO/Redis 全部数据（NFR-10）。
- **记忆保留策略**：L0 原文按会话保留期（默认永久，可配）；`memory_generation_logs` 保留 90 天；`scenes` 活跃场景常驻、归档场景按 `status=archived` 保留；`skills` 保留 head + 最近 N 版（非 head 版本 TTL 可配，默认关闭）；衰减转归档见 §10.1。
- **备份**：Mongo（mongodump）+ Milvus（导出）+ MinIO（镜像）每日；scripts/ 提供脚本。

## 8. Neo4j 图存储设计（FR-26）

> 选型结论见 02 §4（ADR-011）。图与向量**互补而非替代**：向量负责语义相似召回，图负责关系/多跳/结构化（技术栈脑图、论文引用网络）。

### 8.0 图谱解决什么问题（为什么值得引入）

图不是"锦上添花的可视化"，它补的是向量检索的四个结构性盲区。每个场景给出可感知的收益：

| 场景 | 向量检索的局限 | 图谱的解决方式 | 用户可感知效果 |
| :--- | :--- | :--- | :--- |
| 别名/同义归一 | "LangGraph""langgraph""LG" 向量相近但可能分散在多个 chunk | 实体链接把别名 MERGE 到同一 Entity 节点 | 查"LG"也能命中"LangGraph"的全部文档 |
| 概念外延扩展 | chunk 里没写"多智能体编排"这几个字，就召不回 | 查询实体 → 1-2 跳邻居（编排→LangGraph/LangChain/Celery/记忆）→ 经 MENTIONS 拉回相关 chunk | "选个多智能体框架"能带出它依赖的消息队列、记忆方案 |
| 多跳问答 | 单次语义检索答不了"A 依赖 B，B 用了什么" | 沿 DEPENDS_ON/USES 多跳遍历子图 | 直接回答链式关系问题，而非只给相关段落 |
| 经验冲突发现 | 两条结论矛盾的经验语义可能相距很远，向量召回不会并排出现 | 两条记忆都 MENTIONS 同一 Entity → 邻居查询把它们捞到同一子图 | 冲突经验被成对暴露，喂给 §10.6 冲突解决 |
| 脑图/拓扑 | 无法结构化呈现"组成/替代/依赖" | 按 PART_OF/ALTERNATIVE_TO/USES 投影为树 | 技术栈脑图、任务拓扑，支撑创造性思考 |

> **实体消歧是图谱价值的根基**：抽取时同名不同义（"Memory"既指记忆模块又是工具名）必须用 kind + 上下文消歧，否则上表收益全部落空——这是 8.3 抽取管线里最重要的一步。

### 8.1 图模型（Label / 关系）

**节点**（统一携带 `space_id`、`user_id`、`source` 属性用于隔离与溯源）：

| Label | 说明 | 关键属性 |
| :--- | :--- | :--- |
| Document | 文档/论文 | doc_id, title, domain |
| Chunk | 切片（桥接向量与图谱） | chunk_id, text(截断) |
| Entity | 通用实体 | entity_id, name, kind(tech_stack/framework/language/concept/paper/author/case/tool/project) |
| Paper | 论文（从 Entity kind=paper 特化） | arxiv_id, year, venue, authors[] |
| Case | 开发案例/经验 | case_id, summary |
| Memory | 语义记忆（L1/L3） | memory_id, layer, type, importance |
| Skill | 经验资产（FR-32） | skill_id, version |

**关系**：

| 关系 | 方向 | 示例 |
| :--- | :--- | :--- |
| USES | Document/Case → Entity | 项目文档 USES LangGraph |
| DEPENDS_ON | Entity → Entity | LangGraph DEPENDS_ON LangChain |
| ALTERNATIVE_TO | Entity ↔ Entity | Celery ALTERNATIVE_TO arq |
| PART_OF | Entity → Entity | RRF PART_OF 混合检索方案 |
| RELATED_TO | Entity ↔ Entity | 泛化相关 |
| CITES | Paper → Paper | 引用网络 |
| MENTIONS | Chunk/Document/Memory → Entity | 切片/记忆提及实体（检索定位） |
| BIND_TO | Skill → Agent | Skill 装配到 Agent（阶段二 Loadout） |

### 8.2 隔离与规模

- 个人级规模（单实例，万级实体）：**单图 + 属性过滤**（所有查询带 `space_id`，复合索引 `(space_id, kind)`、`(space_id, name)`）。空间级独享图仅在大空间/强合规时启用。
- 删除级联：删文档 → 清理其 Document/Chunk 节点与挂接关系（MERGE 前先统计引用）。

### 8.3 抽取管线（Import 时异步执行）

```
文档切片 → 实体/关系抽取（LLM，JSON schema 见 07 §3.1）→ 批量 MERGE（按 name+kind+space 去重）
        → 属性合并（冲突保留新值+时间戳）→ 写 MENTIONS 关系（chunk_id ↔ entity）
```
- 触发：`kb_import` 完成后异步子任务（Celery）；可配置只对 `domain=dev|paper` 与高价值文档抽取（成本控制）。
- 增量更新：文档重导入时按 doc_id 先删后建（幂等）。
- 质量：抽取失败/置信度低的实体进待审队列（admin 可修正），修正结果回写图谱。

### 8.4 检索集成（混合检索升级）

1. 查询 → 意图/实体抽取（LLM）→ 图谱实体链接（name 模糊 + 向量对齐）；
2. 子图扩展：实体 1-2 跳邻居 + 关联 Chunk/Document（`MENTIONS` 关系）；
3. 与向量召回结果 RRF 融合 → Rerank；
4. 多跳问答（GraphRAG）：先取子图（≤50 节点）转文本进 LLM（阶段二做社区摘要）。

**工作示例（"我要选一个多智能体编排框架"）**：
1. 实体抽取 → `多智能体编排`（concept），图谱实体链接到对应 Entity；
2. 子图扩展 → 邻居 `LangGraph / AutoGen / CrewAI / LangChain / Celery / 记忆系统`（1 跳）+ 各 `ALTERNATIVE_TO` 关系；
3. 经 `MENTIONS` 拉回这些实体出现的 chunk（含技术选型对比、踩坑经验）；
4. 与向量召回（"多智能体框架选型"相关切片）RRF 融合 → Rerank → 生成时带出"LangGraph 依赖 LangChain、Celery 是其队列备选"这类**关系性结论**，而非孤立片段。

### 8.5 脑图/可视化数据

- `mindmap(topic)`：以 topic 实体为中心做 2 层 BFS，按 `PART_OF`/`USES`/`ALTERNATIVE_TO` 投影为树 → 返回 JSON（节点/边/分组）供前端 G6 渲染（06 §8.3）。
- 前端组件：`GraphPanel.vue`（关系图 + 脑图双模式，节点可点击跳转文档/经验）。

## 10. 记忆与经验的数据生命周期（FR-29/31/32）

### 10.1 记忆分级与定期整理

```
写入路径: 对话/任务 → 情景记忆(messages/tasks) ─┐
          显式"记住"/点子捕获 → 语义记忆(memories) ─┤→ 定期整理(夜间, Celery beat)
          经验沉淀(save-from-task) → 语义记忆(dev_case) ┘
                                                       ↓
        整理任务: 情景摘要(会话周报) / 语义去重合并 / 冲突消解 /
                  重要性衰减(半衰期) / TTL 过期 / 经验 supersedes 标记 /
                  实体抽取→图谱链接 / 进展追踪(progress)更新
```

- 整理任务幂等、可重放（按 `(user_id, period)` 记录执行游标），失败重试，产出写审计。
- **整理操作序列（Sleep-time Compute 思路，arXiv:2504.13171）**：① **增量重放**——只处理上次游标后的会话/任务（绝不全量）；② **反思**——对重放内容提炼新 L1/更新旧 L1；③ **压缩**——长会话滚动摘要、重复记忆合并、超阈值归档。三步均设 token 预算封顶（🧪），总成本 ≤ 对话成本的 10%（预算哨兵）。
- **整理预览确认**：整理前生成"预览报告"（将合并/降权/删除哪些），用户确认后执行；未确认则只做低风险项（TTL 过期、纯重复去重）。
- **衰减规则**：语义记忆 `importance = importance × decay^(days/half_life)`，低于阈值转归档（`status=archived`），TTL 到期删除；高频使用/好评的记忆提升 importance（FR-32 自迭代闭环）。
- **去重与合并**：向量相似度 > 0.92 视为候选重复 → 语义比对（LLM 判断等价）→ 合并（保留更完整、更新、高 importance 者，其余记入 `supersedes`）。
- **新旧更替（supersedes）**：新经验入库时若与旧经验同主题且更完整/更新，显式标记旧条目被取代，检索排序降权、页面标注"已被 XX 取代"。
- **用户控制**：记忆全程可见可编辑可删除；对话记忆索引开关（见 04 §7 与 05 §7）；注销级联删除（NFR-10）。

### 10.2 对话记忆 RAG 的取舍（哪些对话值得建索引）

| 对话内容 | 是否入记忆/索引 | 说明 |
| :--- | :--- | :--- |
| 用户陈述的事实/偏好/决策 | ✅ 语义记忆 | 高价值，跨会话复用 |
| 点子/想法/困惑（用户"记下"或 Agent 识别） | ✅ `kind=idea/insight` + `linked_ids` | FR-31，关联 Paper/文档 |
| 学习/研究进展（"读到第 X 章""卡在 Y"） | ✅ `kind=progress` 按主题聚合 | FR-30 进展恢复 |
| 会话级摘要与主题关键词 | ✅ 会话摘要（轻量） | 上下文恢复兜底 |
| 寒暄、临时性指令、敏感信息 | ❌ 不索引 | 隐私与信噪比 |
| 已删除消息/会话 | ❌ 级联清除 | 用户删除即遗忘 |

### 10.3 分层记忆与渐进召回（借鉴 TencentDB-Agent-Memory，ADR-016）

四类记忆映射到 L0-L3（见 04 §7.1）。关键取舍：

- **分层生成**：L0 原文永存；L1 原子由异步 pipeline 从 L0 抽取（LLM，JSON schema）；L2 场景与 L3 画像由 L1 归纳，变化时增量更新（`replace`/`write` 两模式）。
- **渐进召回 + 预算**：稳定部分（persona/scene）入 system 提示（可缓存），动态部分（L1 相关记忆）入 user 前缀；召回预算 `max_results`/`score_threshold`/`max_total_chars`/`timeout` 硬约束，防止记忆反噬上下文。
- **混合检索降级**：BM25（本地 FTS5，无 embedding 也工作）→ embedding（可选）→ hybrid RRF(k=60)；embedding 配置了但不可用时明确报错而非静默降级（fast-fail 可观测）。
- **存储最小化（反过度设计）**：阶段一用 Mongo + BM25 起步，向量库按需接入——与"不过度设计"原则一致。
- **任务拓扑（L2 特化）**：长任务的 Mermaid 认知状态机（taskGoal / progress 0-100 / 节点 status: done|doing|paused|blocked / 认知墓碑记录死胡同），≤4000 字预算，`replace` 增量更新；是"进展恢复 + 防重蹈覆辙"的载体。

### 10.4 记忆生成溯源（借鉴 provenance）

- 每条 L1/L2/L3 记忆记录生成它的 `prompt_id/version/hash` + 输入输出引用（`generation_log` 集合），不存 prompt 正文快照；可按 memory_id 精确溯源、按 prompt 版本回滚重生成。
- 自定义记忆抽取 prompt 分层绑定：`Agent > Team > Instance > 系统内置`；只追加关注点/归纳策略，不修改固定输出协议（L1 JSON / L2 Scene Markdown / L3 Persona）。

### 10.6 经验生命周期决策：新建 / 更新 / 合并 / 取代 / 冲突（FR-32 核心）

新经验 E（来自会话沉淀、外部 Agent 回流、设计复盘）入库的统一决策流程，消除"何时新建、何时更新"的模糊：

```
新经验 E 归一化（实体链接 + 主题向量 + content_hash）
        │
        ▼
① 候选召回：同 space 下，向量 sim>0.85 🧪 的 memory/skill
   + 图谱 MENTIONS 同一实体的经验 + 同 skill_id 的旧版本
        │
        ├─ 候选为空 ──────────────────────────► 新建（memory 或 skill v1）
        ├─ 完全重复（content_hash 命中 或 语义等价）► 丢弃 + use_count+1（不产生新记录）
        ├─ 同类且更新/更完整/更正确 ────────────► 取代（supersedes 旧版，skill 版本+1，旧版降权）
        ├─ 主题同、结论互补（不同侧重点）────────► 合并（保留 source 引用，标注 merged_from）
        └─ 主题同、结论矛盾 ────────────────────► 冲突解决（见下表）
```

**判定准则（可计算，非拍脑袋）**：

| 分支 | 触发条件 | 动作 |
| :--- | :--- | :--- |
| 新建 | 候选为空（sim < 0.85 且无共享实体） | 创建新记录，`source`+`source_message_ids` 溯源 |
| 丢弃 | `content_hash` 命中，或 sim ≥ 0.97 且语义等价（LLM 确认） | 旧记录 `use_count+1`、`last_used_at` 更新 |
| 取代 | 同主题 + 新经验时间更新 + 信息量/正确性更优（Critic 评分更高） | 旧记录记入新记录 `supersedes`，检索降权、页面标"已被取代"；skill 则 version+1 |
| 合并 | 同主题 + 结论互补 + 无矛盾 | 合并为一条，`merged_from` 记录来源 id，保留各自溯源 |
| 冲突 | 同主题 + 结论矛盾 | 见冲突解决 |

> 🧪 **阈值体系（经验起点，需评测校准，见 08 §8.1 #3）**：`sim<0.85 新建 / 0.85–0.97 候选（在候选内判合并、取代、冲突）/ sim≥0.97 等价丢弃`。§10.1 的 0.92（定期整理合并阈值）即"候选区间内的合并判定点"，与本节同属一套体系。

**冲突解决（信任优先 + 人工兜底）**：
1. `trust` 差 ≥ 0.3 🧪 → 高信任者胜出（user 陈述 > agent 推断 > external_agent 回流）；
2. `trust` 相近 → 按新近性 / 使用频次 / 好评率加权比较，仍难决 → **HITL 人工仲裁**（`clarify` 事件给用户二选一，选定者晋升、落选者归档）；
3. 冲突对记录进图谱（两记忆 MENTIONS 同一实体），供后续同类冲突快速定位。

**自迭代闭环（新经验比旧经验好用，且越来越准）**：

```
使用 → 反馈（显式评分 + 隐式 use_count）→ 质量分更新 → 夜间整理 → 晋升/降级/归档
```

- **质量分** `Q = 0.4·trust + 0.2·recency(半衰期) + 0.2·use_rate + 0.2·avg_rating`；检索排序 = 相似度 × Q。
- **晋升**：dev_case 被高频采纳（use_count ≥ 阈值且好评）→ 提炼为 **Skill**（版本化可执行资产，04 §7.2）；design_decision 被反复引用 → importance 提升。
- **降级/归档**：低 Q + 长时间未用 → importance 衰减 → `status=archived`；TTL 到期删除（§10.1）。
- **迭代触发**：每次采纳/差评即时更新 Q；夜间任务做批量重算 + supersedes 链整理 + 冲突重检。
- **可观测**：每次决策写 `audit_logs`（action=memory_merge/supersede/conflict_resolve），`memory_generation_logs` 记录生成 prompt 版本，保证"经验为什么这样变"可追溯。

### 11.1 经验生命周期决策（§10.6 的实现）

```python
Fate = Literal["create", "drop_duplicate", "supersede", "merge", "conflict_ask"]

def decide_experience_fate(new: Experience, candidates: list[Experience],
                           semantic_equiv: Callable[[str, str], bool]) -> tuple[Fate, str | None]:
    """返回 (决策, 目标经验 id 或 None)。纯函数，阈值来自配置（🧪）。"""
    if not candidates:
        return "create", None
    best = max(candidates, key=lambda c: sim(new, c))
    if new.content_hash and new.content_hash == best.content_hash:
        return "drop_duplicate", best.id                    # 完全重复
    if sim(new, best) >= CFG.equiv_threshold:               # 0.97 🧪
        return "drop_duplicate" if semantic_equiv(new.content, best.content) else "supersede", best.id
    if sim(new, best) >= CFG.candidate_threshold:           # 0.85 🧪
        conflict = detect_conflict(new, best)               # 图谱同实体 + 结论极性判断
        if conflict:
            return "conflict_ask", best.id
        if is_superset(new, best) or is_newer_and_better(new, best, critic_score):
            return "supersede", best.id
        return "merge", best.id
    return "create", None
```

### 11.2 混合检索 RRF 融合（04 §12 / 03 §8.4 共用）

```python
def rrf_merge(rank_lists: list[list[str]], k: float = 60.0) -> list[str]:
    """输入多路 id 列表（向量/BM25/图谱扩展），输出融合排序 id。"""
    scores: dict[str, float] = {}
    for lst in rank_lists:
        for rank, rid in enumerate(lst):
            scores[rid] = scores.get(rid, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)
```

### 11.3 记忆召回预算（04 §7.2 的实现）

```python
def apply_recall_budget(lines: list[str], max_total_chars: int,
                        max_chars_per_memory: int | None = None) -> list[str]:
    """截断/丢弃超预算记忆行，返回实际注入的列表（纯函数）。"""
    out, used = [], 0
    for line in lines:
        line = truncate(line, max_chars_per_memory) if max_chars_per_memory else line
        sep = 1 if out else 0
        if used + sep + len(line) > max_total_chars:
            break                                        # 剩余全部丢弃
        out.append(line); used += sep + len(line)
    return out
```
