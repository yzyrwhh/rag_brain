## 2026-08-16 · 智能记忆 · 写入时融合的"增删改查"语义决策（merge / supersede）

**里程碑**：用户实测发现 bug——两条同主题不同方面的经验（"图状态设计用字典就够" vs "做 agent 还是 langgraph 好"）被**覆盖**而非**合并** → 用户明确要求"更新的方式需要改，做增删改查的正确选择"。

| 维度 | 内容 |
| :--- | :--- |
| 修改文件 | `app/services/memory_service.py`（`_consolidate` 重构：LLM 提纯改 JSON 结构化输出 `{action, content}`）、`app/services/supervisor_service.py`（`_match_remember` 前缀清理扩展：冒号+**逗号**） |
| 对应设计 | 03 §10.6 写入时融合：原实现把"互补合并"与"演进取代"都走了**覆盖+supersede**，丢失了"多视角保留"语义 |
| 实现功能 | **增删改查四分支**：① 等价(≥0.8) → **查**（use_count+1 不新增）；② 相关且**互补/多视角** → **改=合并**（LLM 把新旧全部要点合并为一条，旧条目 `merged_from` 记录来源、归档但不标记 supersede）；③ 相关且**演进/替代** → **改=取代**（整合演进脉络，旧条目 `supersedes`+归档）；④ 无关 → **增**（新增）。LLM 失败降级=保守合并（不丢旧要点不覆盖）；JSON 解析失败/action 非法默认 merge |
| 解决痛点 | 同主题不同方面被新覆盖旧（信息丢失）；"记住"指令带逗号（"记住，做agent…"）前缀未清干净 |
| 所用技术 | chat_json（JSON 模式）、action 白名单校验、merged_from/supersedes 双字段区分合并与取代 |

**踩坑**：原 `_consolidate` 一刀切"覆盖最相关 + 其余 supersede"——LLM 提纯 prompt 只说"融合为一条"，模型可能只保留新内容 → 用户复验时旧经验消失。修复要点：**prompt 显式要求区分 merge（全部保留，可用其一/其二组织）与 supersede（演进脉络），且 content 缺失/失败时程序性拼接旧要点保底**。

### 金点子 4：DevAgent = 架构师经验图谱（FR-36）——场景×技术栈×方法，垂直领域可复制

- **来源**：用户判断 DevAgent 本质是"架构师"：什么场景用什么技术栈、技术栈适合什么场景、什么项目用什么开发方法。
- **设计**：用**图组织经验**（Neo4j：Scenario / TechStack 节点 + `SUITABLE_FOR` 关系，扩展 03 §8）；经验入库时抽取"场景→技术栈→适用性"入图；DevAgent 咨询时图谱检索（"什么场景用什么"直接走图，而非纯向量）。
- **复用**：这套"领域经验图谱"模式可复制到审计等 LLM 难渗透的垂直领域（领域实体 + 决策关系图）。
- **实施**：阶段二（图谱验证后，随 03 §8 Neo4j 深化落地）。

### 金点子 5：图谱元模型 + 可插拔本体（FR-36 细化）——多身份/多领域的图设计

- **来源**：用户追问"图和数据层面如何设计"——架构师身份按小程序/前端/后端/Agent 还是按技术栈？律师身份要分很多部法律/地方法？
- **决策**（已落 03 §8.2.1）：
  1. **两个维度分开**：小程序/前端/后端/Agent 是**分类维度（category 属性）**不是实体类型；技术栈/场景/方法才是**知识对象（实体类型）**——分类用于过滤，结构用于存储，加新分类不改 schema；
  2. **元模型固定 + 本体可插拔**：统一 `:Entity{domain,kind,name,category}` + `:REL{type,from,to,domain}`，每领域一个 `ontologies/{domain}.json` 定义 kinds/relations/抽取 schema；
  3. **律师问题自动解决**：`Law` 是实体类型，每部法律/地方法是实例（name=刑法/属地法），`Jurisdiction` 法域是另一种实体，`Law -BELONGS_TO-> Jurisdiction`；
  4. **身份（Identity）**只决定默认本体与默认 domain，数据层不额外建模；
  5. 图存储选**方案 A：通用 Entity/REL + 属性化 kind/type**（扩展性最强，新领域零迁移），应用层 ontology 白名单校验。

### 金点子 6：系统本质定位——经验传承系统，不是 RAG

- **用户三问**：①场景自动识别+逐渐优化？②越用越好用？③本质还是 RAG 做底层？
- **结论**：
  1. **场景自动识别（FR-37）**：像意图识别一样自动判定"发生在什么场景"并关联经验；匹配度随采纳/好评演化、未用关联衰减——场景路由的经验优先级学习；
  2. **越用越好用 = 学习闭环**：使用→反馈→Q 分→写入时融合→检索加权→质量提升→更多使用；与"养小龙虾（数量堆积）"的本质差别是**数量收敛、质量演化**——同主题单条不断更新（supersede/场景累积），绝不无限堆积；
  3. **执行层是 RAG，本质不是**：RAG = 静态文档字典（查了就答、字典不变）；本系统 = 文档（知识库 RAG）+ 经验（写入时融合演化）+ 图谱（场景×技术栈×方法）+ 反馈（学习）四层，本质是"**经验传承与决策系统**"，RAG 只是取用机制。

### 金点子 8：统一错误透传 + 地球仪式 3D 图谱探索视图

- **① 统一错误（已实现 2026-08-16）**：业务错误统一 `AppError`（05 §9 错误体），前端按 code 映射文案；补齐"记住/流式"内部异常处理：AppError 透传真实 message，未知异常记日志 + 通用文案——不再吞成笼统"失败"。
- **② 地球仪式 3D 图谱可视化（FR-36 前端候选）**：知识/记忆展示用 `globe.gl`（three.js）地球仪隐喻——**领域=国家、节点=城市、关系=航线、importance=级别（越重要越大/越高）**，可拖转、缩放；与"领域即图"（03 §8.2.1）语义完全契合。定位：知识库"探索视图"（总览/漫游），非主交互界面（检索/问答仍走列表）；阶段二随 Neo4j 图谱数据落地，先落选型与隐喻约定。

### 金点子 7：智能记忆四件套（FR-37/38/39）——LLM 该介入就介入，图的更新时机=写入时

- **用户五连问**：隐式场景应识别？LLM 介入 token 开销不大但解决问题多？领域由 LLM 判断+相近合并？领域本质是图、图相关性用嵌入/重排？图的更新时机=写入时？

- **用户五连问**：隐式场景应识别？LLM 介入 token 开销不大但解决问题多？领域由 LLM 判断+相近合并？领域本质是图、图相关性用嵌入/重排？图的更新时机=写入时？
- **决策**：
  1. **场景双通道**：正则（显式"X场景"，零成本）优先 + LLM 兜底（隐式表达"什么情况下/哪种项目"，JSON 模式，失败降级空场景）——"记住"是低频操作，LLM 成本可忽略；
  2. **领域 LLM 归属 + 防误判闸门**：高置信(≥0.8)匹配已有领域才归入；低置信归 `general`；**不自动新建领域**（防"每记一条建一个领域"的小龙虾陷阱）；相近领域合并=建议 + HITL 确认（批量迁移不能静默），合并时建跨域节点关联；
  3. **领域=图**：domain 属性划分的 Entity/REL 子图；图/节点相关性判断**复用现有 BGE-M3（嵌入）+ bge-reranker（重排）**——记忆向量化（FR-39，Milvus memory_vectors 已建）是第一步；
  4. **图的更新时机=写入时**：每次记忆/经验写入同步/异步 MERGE 实体关系，夜间整理只做巩固/跨域合并/去重（03 §8.3 抽取管线从 Import 扩展到 Memory）。
