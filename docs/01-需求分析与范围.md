# 01 · 需求分析与范围

## 1. 背景与问题陈述

### 1.1 现状（代码确认）

现有系统是两条独立的 LangGraph 单链流水线：

- **导入管线**（`processor/import_process`）：入口 → PDF/MD 转换 → 文档切分 → 商品名识别 → BGE 向量化 → 入 Milvus。
- **查询管线**（`processor/query_process`）：商品名确认 → HyDE/向量/Web 三路检索 → RRF 融合 → Rerank → 答案输出。

存在以下结构性缺陷：

| 缺陷 | 表现 | 影响 |
| :--- | :--- | :--- |
| 意图硬编码 | 查询必须提取"商品名"，`item_name_confirm` 写死商品语义 | 无法扩展论文、代码、生活场景 |
| 无全局记忆 | 状态是扁平 `TypedDict`，任务状态放内存字典（`task_utils`） | 多轮无上下文；重启丢任务；无持久化 |
| 工具内嵌 | 检索/Web 搜索硬编码在节点内，MCP 是空壳 | 无法动态组合工具 |
| 单用户假设 | 无用户/空间概念 | 无法支撑多用户 |
| 无反思循环 | 单链 DAG，无失败重试、无质量评审 | 复杂任务（论文综述）不可行 |
| 无任务基础设施 | 无队列、无重试、无取消、无成本统计 | 长任务不可靠 |

### 1.2 重构目标

> 从"商品查询 RAG"升级为**多域多智能体平台**，同时以本重构为实践载体，打磨多智能体系统开发的完整工程能力（编排、记忆、工具、评测、可观测性）。

## 2. 干系人与角色

| 角色 | 描述 | 核心诉求 |
| :--- | :--- | :--- |
| 注册用户 | 系统使用者（家庭/个人/团队） | 高效完成研究、开发、生活、知识问答四类任务 |
| 系统管理员 | 部署与运维者（用户本人兼任） | 可观测、可配置、成本可控、数据安全 |
| 第三方服务 | 百炼 LLM、arXiv、电商站点、MCP 服务 | 稳定调用、合规使用 |

## 3. 能力域与用户故事（EPIC）

### EPIC-1 知识域（KnowledgeAgent）—— 重构现有能力

- US-1.1 作为用户，我可以上传 PDF/Markdown/图片等文档到我的空间，系统自动解析、切分、向量化入库。
- US-1.2 作为用户，我可以对"我的空间/共享空间"进行混合检索（向量 + 全文 + 重排）并得到带来源的答案。
- US-1.3 作为用户，我可以给文档打标签、设领域（general/dev/paper/life）、查看导入进度与质量。
- US-1.4 作为用户，我可以创建共享空间并邀请协作者，空间内文档对成员可见。

### EPIC-2 开发域（DevAgent）—— 新增

- US-2.1 作为开发者，我可以咨询技术方案（如"用 LangGraph 做多智能体，状态怎么设计"），Agent 结合我的经验库与网络检索给出方案。
- US-2.2 作为开发者，我可以让 Agent 生成/审查代码，并在沙箱中运行验证（阶段二）。
- US-2.3 作为开发者，我可以让 Agent 把一次开发中的关键决策（技术选型、踩坑、架构图）沉淀为经验条目入库，以后可检索复用。
- US-2.4 作为开发者，我可以查询"某技术栈/框架的适用场景、对比、最佳实践"，答案优先来自我沉淀的案例。

### EPIC-3 研究域（ResearchAgent）—— 新增

- US-3.1 作为研究者，我可以请求"找 10 篇关于 RAG 优化的近三年论文"，Agent 检索 arXiv/Semantic Scholar 并给出带摘要的候选列表。
- US-3.2 我可以对候选论文按相关度/影响力筛选，把满意的论文全文/摘要/元数据存入知识库（paper 域）。
- US-3.3 我可以请求"对已入库的这批论文生成一篇综述"，Agent 规划、分步阅读、产出结构化综述（含引用）。
- US-3.4 我可以对知识库中某主题做"增量追踪"：定期检索新论文并提醒（阶段二）。

### EPIC-4 生活域（LifeAgent）—— 新增

- US-4.1 作为用户，我可以描述需求（"今晚两人份、想吃清淡的、预算 100 内"），Agent 给出外卖/买菜比价推荐清单。
- US-4.2 我可以让 Agent 对比多个平台/商家的价格与评分，生成含链接的清单，我点击外链自行下单。
- US-4.3 我可以让 Agent 根据我的口味偏好与历史清单，做定期采购计划（如每周买菜清单）。
- US-4.4 我可以让 Agent 记住我的常购商品与偏好（记忆系统），推荐时优先考虑。

### EPIC-5 平台能力（横切）

- US-5.1 作为用户，我可以注册/登录，我的数据与其他用户完全隔离。
- US-5.2 我可以看到每个任务的执行进度（步骤树、当前工具调用、消耗 token/费用）。
- US-5.3 当 Agent 不确定（如"哪个商家更好"）时，我可以收到澄清选项并选择，任务继续。
- US-5.4 我可以管理 Agent（启用/禁用工具、调模型）、管理记忆（查看/编辑/删除）、配置第三方集成。
- US-5.5 我可以通过 CLI 完成与 Web 相同的核心操作（对话、任务、上传、检索）。

## 5. 非功能需求（NFR）

| 类别 | 编号 | 指标 |
| :--- | :--- | :--- |
| 性能 | NFR-01 | 快任务（RAG 问答）首 token ≤ 3s，总时长 ≤ 30s |
| 性能 | NFR-02 | 慢任务（综述/批量入库）异步执行，不阻塞 API |
| 性能 | NFR-03 | 检索 P95 ≤ 800ms（不含 LLM 生成） |
| 可靠性 | NFR-04 | 任务失败自动重试 ≥ 2 次；可取消；进程重启后任务可恢复（持久化状态） |
| 安全 | NFR-05 | 全链路数据隔离：检索/上传/记忆/任务均按 `user_id` + `space_id` 过滤 |
| 安全 | NFR-06 | 密码 bcrypt 加盐；JWT access 15min / refresh 7d；密钥加密存储 |
| 安全 | NFR-07 | Prompt 注入防护：文档内容标记为数据，不视为指令；敏感操作需用户确认 |
| 成本 | NFR-08 | 单任务默认 token 预算上限，超限自动降级/中断 |
| 可观测 | NFR-09 | 全链路 trace（LangSmith）；结构化日志；任务失败率、延迟、成本指标 |
| 合规 | NFR-10 | 不代下单、不处理支付；个人信息最小化；删除用户即删除其全部数据 |
| 可用性 | NFR-11 | 单机 Docker Compose 可完整运行；API 无状态可水平扩展 |

## 6. 边界与非目标（明确的"不做"）

- **不代下单、不经手支付**：生活域只做比价推荐、清单、外链跳转。
- **不做移动原生 App**：Web（可 PWA）+ CLI。
- **不接入美团/京东等开放平台下单 API**（阶段一）：资质与合规成本高，仅做技术预研记录。
- **不做流式长对话的状态持久化重放**（阶段一）：任务状态持久化即可，对话重放可选。
- **不做多租户计费/复杂的组织权限**：共享空间成员角色仅 owner/member/viewer 三级。
- **不接入企业级 SSO / 审计合规**：保留扩展点（`audit_logs` 集合）。

## 7. 验收标准示例

- **FR-05 验收**：上传 20MB PDF，任务状态经历 `pending → parsing → splitting → embedding → importing → completed`，前端步骤树可见，失败可重试，完成后 3s 内可检索命中。
- **FR-09 验收**：对 50 条跨域语料（商品、论文、代码、生活）意图识别准确率 ≥ 90%（评测集）。
- **NFR-05 验收**：用户 A 无法通过任何 API 读到用户 B 的文档/记忆/任务；针对检索接口的越权测试全部通过。
